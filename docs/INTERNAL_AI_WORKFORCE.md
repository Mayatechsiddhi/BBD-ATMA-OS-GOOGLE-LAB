Reuse its task ownership, agent/run records, approval and budget facilities if the acceptance gates below pass. Preserve BBD's Next.js/Prisma/Better Auth, tenant RLS, audit, module entitlements, CRM, Clinic and calling services. Do not transplant Paperclip tables, authentication or job execution into the BBD application.

## Proposed six-department organization

One internal BBD company, with the founder/appointed human Board as the sole authority for hiring, credentials, budgets and release decisions. Department owners below are accountable **human roles to appoint**, not claims that staff already exist. AI managers cannot approve their own work. Initially create at most two candidate agents; the other departments are specifications, not active teams.

| Department                    | Accountable owner and candidate roles                                                   | Permitted first outputs                                                                                | Explicit exclusions                                                                                                                                                          |
| ----------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Engineering — first candidate | Human engineering owner; Engineering Draft Analyst. Later separate QA/Security Reviewer | Approved commit/diff review summary, regression checklist, non-applied patch or PR-description draft   | No writes to BBD checkout, git push, PR posting, dependency install, merge, credentials or production operations; AI review does not replace qualified human security review |
| Operations — first candidate  | Human operations owner; Readiness/Runbook Analyst                                       | Sanitized CI status summary, missing-evidence checklist, rollback/runbook draft, incident triage draft | No SSH, cloud console, deploy, resource provisioning, SQL, migration execution, log/trace scraping or infrastructure purchases                                               |
| Sales — deferred              | Human sales owner; Proposal Draft Assistant                                             | Generic service/proposal templates and synthetic pipeline-process suggestions                          | No CRM/client/prospect records, enrichment, outreach, email, calls or WhatsApp                                                                                               |
| Marketing — deferred          | Human marketing owner; Content/Planning Assistant                                       | Draft generic content/calendar and consent checklist                                                   | No customer audiences, ad accounts/spend, social publishing, messages or campaign activation                                                                                 |
| Finance — deferred            | Human finance owner; Policy/Cost Draft Analyst                                          | Public-price estimate templates, internal budget-policy drafts from approved non-client metadata       | No bank/ledger/customer invoices, Razorpay, payments, purchases, subscriptions or financial transactions                                                                     |
| Support — deferred            | Human support owner; Knowledge Draft Assistant                                          | Draft FAQs, issue-classification and synthetic-response templates                                      | No customer tickets/PII, production logs, client conversations, messaging or account changes                                                                                 |

Task lifecycle: human approves a typed, bounded request and immutable input digest → exactly one assigned agent claims it → produces draft artifacts → separate reviewer validates evidence → human accepts/rejects. “Done” means draft accepted, not code merged or a real-world action completed. Use Paperclip checkout/ownership conflicts; do not blindly retry a 409 or steal another run's task. Agent creation, reconfiguration, secrets, connectors, schedules and permission changes require fresh human approval. Initially manual start only: no recurring heartbeats, self-delegation, self-hiring or automatic recovery that starts another paid run.

## Storage, credentials and tenant boundary

Proposed isolation: a separate private Paperclip service/home, dedicated PostgreSQL database and migration/runtime identities, separate secret/master keys and artifact volume, separate cookie origin, and per-agent scratch environments. No service is created now. Prefer a separate network namespace/DB instance for the pilot; at minimum deny all BBD database network access and cross-database grants. Validate the target DB identity before Paperclip startup because its default onboarding can automatically migrate.

The workforce gets **no** RUNTIME_DATABASE_URL, DATABASE_URL, BBD auth/gateway/signing secrets, production/cloud credentials, BBD customer API keys, customer files, raw logs/traces or host home directories. Do not launch it in a shell inheriting BBD .env. No Docker socket, host root, writable BBD checkout or shared Codex auth home. Approved source exports are allowlisted, secret-scanned and human-reviewed; input mount read-only, separate scratch/output mount writable, artifacts size/type/path-limited. Do not run package scripts from an untrusted repository export. Global/private credentials and arbitrary network destinations are unavailable by capability, not merely prohibited in prompts.

One Paperclip company is **BBD internal operations**, not any SaaS organization or customer. Paperclip company/agent/task IDs never confer BBD membership. Real CRM outbox payloads contain customer-linked opportunity IDs even though they contain no names: they are **excluded from initial workforce ingestion**. No real tenant events are forwarded or looked up. Synthetic-only event fixtures and approved repository metadata are the initial inputs. Future customer-facing workforce use requires a separate tenant authority/data-processing design and independent review.

## Minimal BBD-to-workforce contracts

**Proposed contracts only. No endpoint, bridge, consumer or new outbox type is implemented by this document.** Reuse Phase 2A's validated event UUID, versioned envelope, per-scope cursor and producer/consumer idempotency principles. Do not pretend the existing outbox is a generic workforce event bus: it currently accepts only `crm.opportunity.created` v1 and has no durable consumer receipts/checkpoints. Sending an internal workforce task type into it today correctly fails its SQL/validation constraints.

The next sprint should use a file-based, synthetic/approved-repository-metadata hand-off first. A later reviewed contract could register `internal.workforce.draft.requested` v1 with explicit internal ownership/privacy rules and a separate additive migration. Do not reuse a customer organization to bypass missing internal scope, change the existing CRM event payload, execute raw INSERTs, or give Paperclip database access. No customer events are forwarded until separate approval.

Proposed private adapter API (not a BBD public route): `POST /internal/workforce/draft-requests` accepts the following strict allowlisted shape; `GET /internal/workforce/draft-results/{requestId}` returns draft metadata only. Caller identity/scope is authenticated and mapped server-side; caller-supplied company IDs, tenant IDs, model config, shell commands, URLs, tools and SQL are rejected. Until that API is approved, the same JSON is a local fixture file, not a listener.

```json
{
  "schema": "bbd.workforce.draft.requested.v1",
  "requestId": "00000000-0000-4000-8000-000000000001",
  "scope": "bbd-internal-only",
  "department": "ENGINEERING",
  "taskKind": "review-summary",
  "source": {
    "kind": "approved-repository-metadata",
    "repository": "bloomdigital369-hue/BBD-MASTER-ATMA-OS",
    "commit": "<approved-immutable-commit-sha>"
  },
  "inputArtifact": "sha256:<approved-sanitized-manifest-digest>",
  "approvalRef": "<human-approval-record>",
  "outputKind": "markdown-draft",
  "expiresAt": "<UTC-expiry>",
  "limits": { "maxRunSeconds": 300, "maxSpendUsdCents": 25 }
}
```

Validate enum combinations (initially ENGINEERING/review-summary and OPERATIONS/readiness-checklist), expiry, approved commit/input hash, size limits and prior approval. Artifact IDs resolve from a private allowlisted store, never arbitrary URLs/paths; block traversal, symlinks and server-side request forgery. Treat source comments, issue text, repository instructions and model output as untrusted data. Commands and approval decisions are not accepted from those artifacts.

Proposed result: `{schema: "bbd.workforce.draft.result.v1", requestId, draftId, sourceCommit, artifactDigest, outcome: "draft_ready" | "blocked", requiresHumanReview: true, evidenceRefs: [...]}`. Markdown or inert patch output only, <=64 KiB initially; validate digest and manifest-relative paths. No executable attachments, secrets, customer identifiers, raw transcripts or “approved/merged/deployed” result states. Any later patch application or GitHub publication is a separate human action/approval; a generated patch is not executed.

Future adapter translation can reuse native Paperclip `POST /api/companies/{companyId}/issues`, issue checkout, issue review/approval and activity APIs. Use one allowlisted internal company/project/agent mapping, not a caller-selected Paperclip company. Agent authentication is a short-lived run JWT; mutating requests carry the matching `X-Paperclip-Run-Id` required by the inspected protocol. Agent role can claim/update its assigned task/draft only; cannot manage agents, connectors, budgets or board decisions. Endpoint/permission contracts must be fixture-tested against the pinned release before use. The source includes issue-create idempotency records, but this review does **not** certify the create-endpoint wire semantics/retention for a bridge.

Maintain a separate bridge receipt keyed by `(internalScope, consumerId, requestId)` and input digest; same key/different input is rejected, same input returns the existing draft/task reference. Store receipts/checkpoints in workforce-owned storage, never shared BBD tenant tables. Do not advance event progress before durable safe hand-off; use provider/task idempotency and reconcile crash windows rather than claiming exactly once. Initial file fixtures create no live Paperclip requests. No BBD callback may mutate business data, entitlement flags, roles, payments or deployment state.

## Approval, audit and stop controls

1. Founder approves the exact request, input classification/digest, owner, sandbox profile and budget **before** a run. A changed input/config/credential or expired approval requires fresh approval.
2. Engineering/Operations may read only approved metadata and produce drafts. No automated GitHub issue/comment/PR write or public publication. A future GitHub App must be selected-repository, metadata/contents read-only; no Actions, administration, merge or billing write scopes.
3. Independent reviewer inspects output/diff/tests and security-sensitive proposals. Agents never approve their own output; AI review supplements, not replaces, required qualified human review. Founder acceptance does not automatically deploy or merge.
4. Record request ID, scope/company, department, owner, source/input digest, prompt-template version, agent/run ID, approved capabilities/budget, approval identity/expiry, start/end/outcome, reported/reserved cost, artifact digest and human disposition. Redact values; no credentials or customer payloads in prompts, logs or exports. Retain private draft artifacts provisionally 30 days and non-secret audit metadata 180 days, subject to an approved retention policy; scratch cleanup after seven days. No cleanup job is configured now.
5. Paperclip activity records are useful evidence but not proven append-only/tamper-resistant under a privileged controller. A later audit export/backup design must preserve BBD-side request/approval records separately. Test secret redaction, restore and revocation before activation.
6. Kill switch: pause agents/schedules, cancel in-flight runs, revoke bridge/provider credentials and deny egress. Do not assume a UI pause immediately cancels a provider request already sent; reconcile its final cost/output before resuming.
