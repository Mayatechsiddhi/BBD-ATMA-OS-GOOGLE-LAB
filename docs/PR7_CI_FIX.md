## Exact reproduction and cause

Line 72 waits for the post-login organization page in account(). Four fixture accounts are registered and signed in during setup. Their browser UI requests previously had no separate network identity, so all sign-ins shared loopback. Signup-only headers tried to distinguish users as 2001:db8:<run>::1, ::2, etc., but Better Auth deliberately normalizes IPv6 hosts to /64; those headers also shared a rate bucket.

The pinned Better Auth 1.7.11 default special rule limits sign-up/sign-in paths to three attempts per ten seconds, overriding the general 30/minute setting for these paths. A fast runner can execute four fixture sign-ins within that window. The fourth correctly returns HTTP 429. AuthForm correctly stays on sign-in when authentication is rejected; the test then incorrectly waits for a successful-login redirect and reports only a navigation timeout.

Control reproduction used CI=true, GITHUB_ACTIONS=true, UTC, Node 24.19.0, the committed workflow's HTTP → curl warm-up → browser ordering, the pinned app/dependencies/PostgreSQL/Mailpit and isolated local app/suite databases. Loopback binding replaces 0.0.0.0 for workspace safety; canonical origin remains http://localhost:3000. An auth-route precompile control made the fast setup reproducible without changing fixtures or limits. Server log sequence: sign-in 200, 200, 200, then 429, followed by the same line-72 20000-ms waitForURL failure. This confirms rate limiting, not an incorrect successful-login URL or a tenant authorization defect.

A separate live probe sent malformed requests with host suffixes ::1 through ::4 in one /64: responses were [400,400,400,429]. A distinct /64 returned 400, proving an independent bucket. Malformed requests created no users and sent no verification emails. Local Chromium is 154.0.8037.57 rather than hosted 156; this is not a claim of identical runner/browser binaries or direct access to hosted network logs.

- Add unit checks for valid/distinct fixture /64s and invalid fixture inputs. Add actual HTTP browser regressions for both sign-up and sign-in: three malformed requests accepted as validation failures, fourth throttled with retry guidance, different /64 independent. Rate limiting is neither disabled nor relaxed.
- Include sign-in/signup/recovery GET pages in the existing CI precompile list. This addresses a separately reproduced local no-JavaScript cold-page compilation timeout, not the hosted line-72 cause. The fixed fake reset token performs no account mutation. Precompile the calling SSE handler with an anonymous request and require HTTP 401; this opens no stream and cannot access a tenant. A subsequent full run reached calling only after all clinic/opportunity assertions passed, but first-use handler compilation outlasted its unchanged 15-second live-connection assertion. Assertions, 15-second request/control deadlines, 20-second navigation checks, 20-second HTTP mutation bounds and overall CI timeout remain unchanged.

No application authentication/redirect logic, trusted origins, cookie/security settings, roles/RLS, schema, dependency or production configuration changes. Fixture headers are restricted by the existing localhost-only test guard; production proxy trust policy is not changed.
