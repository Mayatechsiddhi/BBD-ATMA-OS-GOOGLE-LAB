## Implemented scope and identities

`src/modules/internal-workforce` is a closed, process-local **mock contract harness**, not a production workforce controller, real AI execution or customer-facing ATMA service. It imports only Zod, Node crypto and its own modules. No shell/process, filesystem, environment/credentials, fetch/network, database, arbitrary callback/handler, Paperclip SDK or model APIs are called or exposed by this import tree. This library does not sandbox its Node host. No UI, route, Server Action, scheduled worker or service singleton instantiates it. Local regression commands still use existing localhost synthetic PostgreSQL/Mailpit/Next fixtures; those test tools are not harness capabilities.

One trusted constructor policy fixes an internal company ID and opaque actor bindings, roles and departments. A request's company ID is an untrusted selector and must match this policy. No BBD customer organization ID, membership, session, CRM event or payload is accepted. Distinct harness instances have distinct company-scoped stores; identical task IDs in another company confer no access. Missing/foreign tasks and unknown callers deny without exposing their contents. This is a testable internal scope boundary, **not production authentication or database RLS**. Trusted callers supply actor IDs from their own control context; nothing here authenticates an arbitrary HTTP identity.

The `bbd.workforce.draft.requested.v1` request contains canonical lowercase UUID task/correlation IDs, `bbd-internal-only` company scope, department/task kind, a fixed synthetic repository/commit/artifact digest, initial PENDING approval and QUEUED execution states, UTC creation/expiry and bounded limits. The earlier proposal's `requestId` is concretized as `taskId`; correlation is separate tracing/grouping identity. No deployed wire contract changes because the predecessor was a proposal only.

Only ENGINEERING/review-summary and OPERATIONS/readiness-checklist are available. Two closed synthetic fixture digests are allowed. There is no free text, prompt interpreter, file path, URL resolver, tool/model/provider argument, customer lookup or caller-defined artifact. Strict nested objects reject extra fields, credentials, SQL, shell commands, unsupported departments/types and self-approved/requested terminal states. This is an allowlist, not a claim that a blacklist can identify all secrets. The fixed public repository commit is approved metadata identifying the fixture; no repository is actually read. New real inputs must not be admitted by widening a validator alone.

## Approval and state machine

| Role                      | Permitted harness actions                                                                                                            |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| REQUESTER                 | Submit and inspect only its own department-scoped tasks                                                                              |
| APPROVER                  | Inspect/approve/reject/revoke within assigned departments, read department-filtered audit metadata, pause/resume the company harness |
| OPERATOR                  | Inspect/execute/request retry within assigned departments                                                                            |
| Unknown or customer actor | Nothing                                                                                                                              |

No role automatically inherits another. One actor cannot have duplicate constructor bindings or submit and approve the same task. Actor/role/approval identity cannot be supplied in the request. Command input requires the expected private-record version and exact request digest; only the approver command creates the approval UUID. The original parsed request is immutable within the private record and remains the approval's hash basis. Returned snapshots/results/policy inputs/audit reads cannot mutate private state.

Approval states are PENDING → APPROVED, PENDING → REJECTED, or APPROVED → REVOKED. Rejection/revocation cancels the task and prevents execution/retry/reapproval; a fresh request/approval is required. Revoking a completed mock removes its stored result from future reads but cannot retract copies already returned. Read-only inspection of history and identical submission replay remain possible after expiry/pause; they never start work.

Execution: QUEUED → RUNNING → DRAFT_READY, RETRYABLE_FAILURE or FAILED. Only an explicitly approved, unexpired, unpaused QUEUED task may run. A transient failure permits a separate, version-checked OPERATOR retry command back to QUEUED; there is no automatic retry, backoff, timer or retry loop. A failed/ready/cancelled task cannot be retried. Every retry rechecks approval, expiry, pause and remaining attempts. Commands that request arbitrary target states do not exist.

The default test policy grants at most three attempts per task (requests may lower this), bounds a declared run budget to 1–300 seconds, and requires literal model-spend budget zero because no model is called. Request lifetime is positive and at most fifteen minutes; future-dated/expired submissions and stale approvals fail closed. The mock is synchronous and fixed-size; its post-compute elapsed-time check is not an OS preemption or asynchronous cancellation guarantee. A future real adapter needs separately enforced wall-clock/token/provider budgets. Do not map this mock's zero-spend field to Paperclip's zero budget: the inspected Paperclip policy treats zero as disabling enforcement.

Only the trusted constructor can configure bounded mock transient/permanent failure counts; an agent/request cannot select a failure plan or inject an executor. Unexpected adapter exceptions are recorded as sanitized terminal failures, not leaked error messages. The harness independently revalidates even the mock's returned result before publishing DRAFT_READY, so a forged identity/scope/digest/result is refused.

## Idempotency, bounded state and audit

- `(companyId, taskId)` identifies an immutable request. Identical submission by the same requester returns the existing current snapshot without executing or appending another audit. Changed input/owner under that ID conflicts. A separate `(companyId, correlationId, department, taskKind)` guard prevents a duplicate logical task under a new task ID; Engineering and Operations may share a correlation for distinct tasks.
- Repeated execution after DRAFT_READY is explicitly rejected as ALREADY_EXECUTED, not silently run again. A retry advances only from a transient failure and never resets the attempt counter. There is no public status setter.
- Synchronous private-map operations cannot interleave at an await or call an injected arbitrary handler. The ledger reserves audit capacity before mutating state (two slots for start/terminal execution). Task count is at most 64, principal bindings at most 20, audit entries at most 512. Capacity exhaustion rejects without starting a task or partially changing its state. No pruning/reset is exposed to callers.
- In-memory audit entries have a version, per-instance sequence, internal company, actor, task/correlation, request digest, department, status/approval/attempt and timestamp. They contain no raw request body, draft text, credentials or customer data. Readers receive copies and can see only their granted departments (company pause metadata is global).
- These receipts, permissions, pauses and audits are **not durable across processes/restarts**. They do not coordinate distributed agents, prove exactly once or provide tamper-resistant archival. No human security approval is represented by an in-memory test principal. Do not deploy this harness or feed it real work.

## Result contract and Paperclip boundary

`bbd.workforce.draft.result.v1` binds task, correlation, internal scope, department, source commit, request digest, approval ID and attempt. It always reports `mock: true`, `requiresHumanReview: true`, APPROVED approval and DRAFT_READY execution. The artifact is one of two fixed inert Markdown strings and its SHA-256 digest, held only in memory. There are no URLs, executable attachments, financial/deployment statuses or automatic publishing. The caller must inspect the task snapshot to distinguish failure from a valid draft; FAILED does not carry a fabricated success result.

No real CRM outbox event is consumed or republished. The existing SQL outbox still accepts only `crm.opportunity.created` v1; no new workforce type or migration bypass is introduced. Customer-linked opportunity IDs remain excluded. Internal roles are not BBD tenant OWNER/ADMIN/DISPLAY roles, and the mock is not added to the customer module registry.

A future Paperclip adapter must be separately approved, not installed as a replacement function or arbitrary callback. Preserve this request/result boundary, authenticate a dedicated internal control principal, map only an allowlisted private company/project/task owner, store durable per-company/per-consumer receipts/checkpoints outside BBD tenant databases, and reauthorize approval/scope at dispatch. Qualify native request ownership, JWT/run headers, idempotency retention, retries, cancellation, unknown-cost refusal and output redaction with fault tests. Disable the inspected sandbox-bypass default, reject unsafe extra arguments, use positive real budget caps with independent provider controls, separate homes/credentials/storage and blocked BBD database access. No model/API/agent/secret/HTTP transport, Paperclip package, shell adapter, installer or cloud resource is authorized by this harness.
